# GridGo 服务器部署手册（Linux + Docker，复用 OJ 基础设施）

> 目标环境：Linux 服务器（Ubuntu 22.04/24.04 或 Debian 12 均可），Docker Engine + compose 插件。
> **与 OJ 同机部署**：数据库与缓存**完全复用** OJ 已运行的容器，GridGo 不新起 postgres / redis。
> 部署形态：2 个 GridGo 自有容器 —— `deploy-gridgo-server`（FastAPI + uvicorn :8001）与
> `deploy-gridgo-web`（nginx，容器内 :80 → 宿主机 **81**，站点挂**根路径**）。
> 对外入口：`http://<服务器IP>:81/`（80 端口已由 OJ 占用，GridGo 用 81）。

## 1. 部署架构

```
公网 → http://<服务器IP>:81/  → nginx（deploy-gridgo-web 容器，GridGo 唯一入口）
                                  ├─ /            前端 dist 静态托管（SPA try_files 回退 index.html）
                                  │               （前端请求全是相对路径：REST /api/v1、WS /ws/game）
                                  ├─ /api/  ───── 反代 → server:8001（不剥离前缀，后端路由自带 /api/v1）
                                  └─ /ws/   ───── 反代 → server:8001（长连接，read timeout 3600s）
                                                        │
                                                        │ 同一 docker 网络 deploy_ojnet
                                                        ▼
                       ┌────────────────────────────────────────────────┐
                       │ 复用 OJ 的基础设施（本项目不新起）              │
                       │  deploy-postgres-1:5432   库 gridgo（用户 gridgo）│
                       │  deploy-redis-1:6379      GridGo 用 db1（OJ 用 db0）│
                       └────────────────────────────────────────────────┘
```

要点：

- GridGo 的 server 容器**不发布任何宿主机端口**，只在 compose 网络内以服务名 `server:8001` 供 web 反代；
- 跨容器连接全部走容器名/服务名（`deploy-postgres-1`、`deploy-redis-1`、`server`），不依赖 host.docker.internal；
- GridGo 通过 **external 网络** `deploy_ojnet` 接入 OJ 的网络，**不创建、不删除**该网络；
- 无自有数据卷：业务数据落在 OJ 的 PG（库 `gridgo`）与 Redis（db1），因此 GridGo 侧
  `down` / 重建容器**不会丢数据**（也**不需要**、不应使用 `down -v`）。

## 2. 前置：OJ 必须已在这台服务器上运行

GridGo 的一切外部依赖都由 OJ 提供，部署前请确认：

| 依赖 | 来源 | 校验命令 |
|---|---|---|
| 网络 `deploy_ojnet` | OJ 的 compose 项目网络 | `docker network inspect deploy_ojnet` |
| PostgreSQL `deploy-postgres-1` | OJ 的 docker-compose.yml（自动名，无 container_name） | `docker ps --format '{{.Names}}' \| grep deploy-postgres-1` |
| Redis `deploy-redis-1` | 同上 | `docker ps --format '{{.Names}}' \| grep deploy-redis-1` |

校验一把过：

```bash
docker network inspect deploy_ojnet >/dev/null && \
docker ps --format '{{.Names}}' | grep -E '^deploy-(postgres|redis)-1$'
# 期望输出两行：deploy-postgres-1 / deploy-redis-1
```

> 若缺失，先在 `/home/deploy/OJ/deploy` 下把 OJ 起起来：
> `docker compose -f docker-compose.yml -f compose.prod.yml up -d`
> GridGo 的部署脚本会在缺网络/缺容器时**直接报错退出**，不会偷偷新建一套数据库。

## 3. 服务器环境准备

Docker 与 compose 插件（OJ 部署时通常已装好，可跳过）：

```bash
docker --version          # ≥ 24
docker compose version    # compose 插件 v2
sudo timedatectl set-ntp true    # 时间同步（JWT 有效期、对局时间戳依赖）
```

依赖下载慢时配镜像加速器（`/etc/docker/daemon.json` 的 `registry-mirrors` 后
`sudo systemctl restart docker`）；本项目的 server 镜像内置了 aliyun 的 apt / pip 源，
web 镜像内置了 npmmirror 的 npm 源，海外服务器可自行删掉这些行。

## 4. 获取代码

```bash
cd /home/deploy
git clone https://github.com/LSM-bit/Gridgo.git
cd GridGo
```

部署资产全部在 `deploy/` 目录下：

```
deploy/
├── docker-compose.yml      # base：server 服务 + external 网络 deploy_ojnet
├── compose.prod.yml        # override：web 服务（81:80，对外入口）
├── server.Dockerfile       # 后端镜像（alembic + seed + uvicorn）
├── web.Dockerfile          # 前端镜像（pnpm build → nginx 托管）
├── nginx/default.conf      # 站点 nginx（根路径托管 + /api/、/ws/ 反代 → server:8001）
├── gridgo.env.example      # 环境变量模板
├── gridgo.env              # 实际密钥（gitignore，不入库）
├── deploy-remote.sh        # 一键部署（生成密钥 + 建库/建用户 + 构建启动）
└── update.sh               # 日常更新（git pull + 重建启动）
```

## 5. 密钥配置（deploy/gridgo.env，已 gitignore）

### 5.1 自动生成（推荐）

`deploy-remote.sh` 在 `gridgo.env` 缺失时会自动 `cp` 模板并填充随机值：

```bash
PG_PASSWORD=$(openssl rand -hex 24)   # 写入 DATABASE_URL
JWT_SECRET=$(openssl rand -hex 32)    # 写入 JWT_SECRET_KEY
SERVER_IP=$(curl -fsS ifconfig.me)    # 写入 CORS_ORIGINS
chmod 600 gridgo.env
```

### 5.2 手工配置

```bash
cd deploy
cp gridgo.env.example gridgo.env
openssl rand -hex 24   # → 替换 <POSTGRES_PASSWORD>
openssl rand -hex 32   # → 替换 <openssl rand -hex 32>
vi gridgo.env          # <服务器IP> 换成公网 IP
chmod 600 gridgo.env
```

### 5.3 两个硬约束（踩了会起不来）

| 约束 | 说明 |
|---|---|
| **只能出现后端已声明的键** | 后端 Settings 是 `extra=forbid`（pydantic-settings）；`gridgo.env` 里写了 `app/core/config.py` 未声明的键（例如 `POSTGRES_USER=...`），容器会直接 `ValidationError` 退出。建库所需信息一律从 `DATABASE_URL` 解析。 |
| **库/用户/密码三处一致** | `DATABASE_URL` 里的 user/password/db 就是 PG 里要创建的角色与库；改这里的密码必须重跑 `deploy-remote.sh`（脚本会 `ALTER ROLE ... PASSWORD` 同步） |

`gridgo.env` 关键项一览：

```ini
DATABASE_URL=postgresql+asyncpg://gridgo:<密码>@deploy-postgres-1:5432/gridgo
REDIS_URL=redis://deploy-redis-1:6379/1
JWT_SECRET_KEY=<随机 64 hex>
CORS_ORIGINS=["http://<服务器IP>:81","http://127.0.0.1:81"]
HOST=0.0.0.0
PORT=8001
DEBUG=False
```

## 6. 在 OJ 的 PostgreSQL 里创建 gridgo 库与用户

`deploy-remote.sh` 已内置这一步（幂等），也可手工执行：

```bash
SU=oj    # OJ 的 PG 超级用户（= OJ deploy/api.env 的 POSTGRES_USER；脚本会自动探测）
docker exec -i deploy-postgres-1 psql -v ON_ERROR_STOP=1 -U $SU -d postgres -c \
  "CREATE ROLE gridgo LOGIN PASSWORD '<gridgo.env 里的密码>'"
docker exec -i deploy-postgres-1 psql -U $SU -d postgres -c \
  "CREATE DATABASE gridgo OWNER gridgo ENCODING 'UTF8'"
docker exec -i deploy-postgres-1 psql -U $SU -d gridgo -c \
  "ALTER SCHEMA public OWNER TO gridgo"
```

说明：

- 库名、用户名均为 **gridgo**，与 OJ 的 `oj` 完全隔离（不同 database，不会互相影响表结构）；
- 脚本重复执行安全：角色/库存在时只做 `ALTER ROLE ... PASSWORD`、跳过 `CREATE DATABASE`；
- Redis 隔离：GridGo 固定用 **db1**（`REDIS_URL=.../1`），OJ 用 db0，键空间互不可见。

## 7. 启动

```bash
cd /home/deploy/GridGo
bash deploy/deploy-remote.sh          # 一键：环境检查 → 生成密钥 → 建库 → 构建启动 → 验证
```

或手工分步：

```bash
cd /home/deploy/GridGo/deploy
docker compose -f docker-compose.yml -f compose.prod.yml up -d --build
docker compose -f docker-compose.yml -f compose.prod.yml ps
# 期望：deploy-gridgo-server (healthy) + deploy-gridgo-web (healthy/up)
```

首次构建约 3~10 分钟（server 装 pip 依赖、web 跑 pnpm install + vite build）。
`server` 容器启动时自动串行执行：

```
alembic upgrade head            → 建表/迁移（幂等）
python -m scripts.seed_classic_map  → 经典地图种子（幂等）
uvicorn app.main:app --port 8001    → 启动服务
```

任一步失败容器即退出，由 `restart: unless-stopped` 反复重试；**容器 healthy 隐含迁移与种子都已成功**。

## 8. 首次启动验证

```bash
# 1. 迁移与种子日志（期望看到 Running upgrade ... 与种子插入）
docker logs deploy-gridgo-server | grep -E "Running upgrade|classic"

# 2. 后端健康（容器内）
docker exec deploy-gridgo-server python -c "import urllib.request;print(urllib.request.urlopen('http://127.0.0.1:8001/health').read())"
# 期望：b'{"status":"ok"}'

# 3. 站点与 API 入口（宿主机）
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:81/                 # 200（index.html）
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:81/profile          # 200（SPA 回退）
curl -s http://127.0.0.1:81/api/v1/auth/login -X POST -H 'Content-Type: application/json' \
  -d '{"username":"nobody","password":"x"}' -w "\n%{http_code}\n"             # 401/422 = 反代链路通

# 4. 数据确实落在 OJ 的 PG 里
docker exec -i deploy-postgres-1 psql -U gridgo -d gridgo -c "\dt" | head -20  # 应看到业务表
```

浏览器验收：

| 项 | 操作 |
|---|---|
| 注册/登录 | 打开 `http://<服务器IP>:81/`，注册新账号并登录 |
| 建房间 | 创建房间、切换地图（经典地图种子已就位） |
| 实时对局 | 另一浏览器/设备加入房间，开局后走子、聊天正常（验证 `/ws/` 反代） |
| 个人页 | 战绩、排行榜能正常拉取（验证 stats/records 接口） |

## 9. 防火墙与访问

```bash
sudo ufw status              # 已启用则：sudo ufw allow 81/tcp
# 云服务器还需在控制台安全组放行 81/tcp
```

对外地址：`http://<服务器IP>:81/`（无域名时）；有域名（如 `gridgo.example.com`）时，
把 `deploy/nginx/default.conf` 的 `server_name _;` 改成域名，再
`docker compose -f docker-compose.yml -f compose.prod.yml up -d --build` 重建 web。
HTTPS 模板见 `default.conf` 文末预留段（证书挂进 web 容器后启用）。

## 10. 日常运维

### 10.1 更新上线

```bash
cd /home/deploy/GridGo
bash deploy/update.sh         # git pull --ff-only → 重建 deploy-gridgo-server / deploy-gridgo-web
```

脚本等价于「拉代码 → 校验 `deploy_ojnet` → `docker compose ... up -d --build`」，
**不 down、不加 -v**，因此 OJ 的 postgres/redis 与数据完全不受影响。
数据库结构变更无需手工操作：server 容器每次启动都会跑 `alembic upgrade head`。

### 10.2 日志与状态

```bash
cd /home/deploy/GridGo/deploy
docker compose -f docker-compose.yml -f compose.prod.yml ps
docker logs -f deploy-gridgo-server      # 后端（uvicorn / 访问日志）
docker logs -f deploy-gridgo-web         # nginx
docker logs --tail 200 deploy-gridgo-server | grep -i error
```

### 10.3 重启 / 单独重建

```bash
docker restart deploy-gridgo-server                  # 只重启后端（会重跑幂等迁移+种子）
cd /home/deploy/GridGo/deploy && docker compose -f docker-compose.yml -f compose.prod.yml up -d --build web
```

### 10.4 备份（每天 cron 建议）

```bash
# 只备 GridGo 自己的库（OJ 的库由 OJ 侧备份）
docker exec deploy-postgres-1 pg_dump -U gridgo -d gridgo > gridgo_backup_$(date +%F).sql
```

### 10.5 与 OJ 共享 Redis 的注意事项

GridGo 用 db1、OJ 用 db0，**仅做键空间隔离**；OJ 的 redis 启动参数为
`--maxmemory 64mb --maxmemory-policy allkeys-lru --save ""`，即：

- **内存淘汰是全实例范围的**（`allkeys-lru` 不区分 db）：GridGo 若在 Redis 里堆大量 key，
  可能把 OJ 的 key 一起挤掉；
- **无持久化**（`--save ""`）：redis 重启后两边缓存均清空，属预期（两侧数据都以 PG 为准）。

因此 GridGo 侧应避免把大对象长驻 Redis；对局流量高峰前建议与 OJ 运维确认内存余量。
如需独立配额，只能改用独立 redis 实例（不属于当前方案）。

## 11. 容器命名与目录约定（对齐 OJ deploy）

| 服务 | 容器名 | 类型 / 定义位置 |
|---|---|---|
| server | `deploy-gridgo-server` | GridGo 专属 · `deploy/docker-compose.yml` |
| web | `deploy-gridgo-web` | GridGo 专属 · `deploy/compose.prod.yml` |
| postgres | `deploy-postgres-1` | **OJ 提供**（自动名，本项目不定义、不管理） |
| redis | `deploy-redis-1` | **OJ 提供**（同上） |

- 显式容器名全局唯一、不带 project 前缀：本机若要用 `-p gridgoprod` 再起一套会与服务器无关，
  但**在本机**会与根目录 `docker-compose.yml` 的 `gridgo-server`/`gridgo-web` 并存冲突（端口），
  本机调试请勿与 deploy 目录同时运行；
- 按容器名操作：`docker logs -f deploy-gridgo-server`、`docker exec -it deploy-gridgo-web sh`；
  compose 系列命令仍按**服务名**寻址：`docker compose ... logs server`；
- `deploy/gridgo.env` 已被 `.gitignore` 忽略（`git check-ignore deploy/gridgo.env` 应有输出）。

## 12. 常见问题

| 现象 | 处理 |
|---|---|
| `network deploy_ojnet declared as external, but could not be found` | OJ 未运行：先起 OJ（§2），不要手工 `docker network create`（会与 OJ 的 compose 网络定义冲突） |
| 容器起不来，日志 `Extra inputs are not permitted` | `gridgo.env` 里写了后端未声明的键（如 `POSTGRES_USER`），删掉多余行后 `up -d` |
| server 反复重启，日志 `Connection refused` / `could not connect to server` | 外部 PG 未就绪或库/用户不存在：确认 `deploy-postgres-1` 在跑，并重跑 `bash deploy/deploy-remote.sh` 完成建库建用户 |
| `password authentication failed for user "gridgo"` | PG 里的密码与 `gridgo.env` 的 `DATABASE_URL` 不一致：重跑 deploy-remote.sh（会 `ALTER ROLE` 同步密码） |
| `permission denied for schema public` | PG15+ 的 public schema 归属问题：执行 §6 的 `ALTER SCHEMA public OWNER TO gridgo` |
| 81 端口打不开 | 安全组/防火墙未放行 81，或容器未起：`docker ps` + `ss -lntp \| grep 81` |
| 页面能开、接口 502 | 后端未 healthy：`docker logs deploy-gridgo-server`；确认 nginx 代理目标是 `server:8001` |
| 页面 404、刷新路由 404 | nginx `try_files ... /index.html` 回退被改动：恢复 `deploy/nginx/default.conf` 后重建 web |
| WebSocket 连不上（对局卡住） | `/ws/` 的 `Upgrade`/`Connection` 头或超时被改；同时确认浏览器访问的是 81 端口（同源 ws） |
| OJ 被影响 / 两边端口打架 | GridGo 只用 81，绝不占 80；若 `81:80` 被改回 `80:80` 会与 OJ 冲突，务必保持 81 |
| 更新后容器名冲突、端口被占 | 历史自动名容器（`deploy-server-1` / `deploy-web-1`）仍存活：`docker rm -f` 掉后重新 `up -d --build`（`update.sh` 已内置） |
| 拉镜像/依赖超时 | 配镜像加速器；server 已内置 aliyun apt/pip 源，web 已内置 npmmirror |
| 想改端口（如 82） | 改 `deploy/compose.prod.yml` 的 `81:80` → `82:80`，并同步放行安全组；站点路径不变 |
